1. The Prototype

Everything in Sections 1 to 3 of the first post is implemented in a rustc prototype as four incomplete features, struct_args, struct_args_pattern_elision, parameter_type_elision, and named_arguments, each gated separately so they can be judged separately. Defaults and .. also need #![feature(default_field_values)], which landed in rust-lang/rust#129514. The examples in both posts that compile come from it, and Prototype gaps lists where it falls short.

It’s about 2,000 lines of changes to the compiler and tools. The idea is to turn the new syntax into an ordinary struct, struct pattern, or struct literal as early as possible, so most of the compiler, like privacy, borrow checking, and MIR building, doesn’t see anything new. Internally an anonymous struct is called a record, which is where names like TyKind::Record and {record@..} come from. The name also leaves the door open for extending them later, toward the record types of Section 3.

The core feature

#![feature(struct_args, struct_args_pattern_elision, default_field_values)]

fn f(a: i32, struct { x: i32, y: i32 = 0 }) {}
f(0, _ { x: 1, .. });
  • Parsing. struct { .. } is a new AST type, TyKind::Record, which holds the fields. It’s only parsed as a parameter’s type or a field’s type inside another one, and anywhere else it’s an error. A parameter that’s just the type gets the pattern <_>::_ { x, y }, which _ { x, y } also parses to. An elided parameter type is the type its pattern spells out, so Point { x, y } becomes Point { x, y }: Point, and &T(x) becomes &T(x): &T. And _ { .. } in an expression is a struct literal whose path gets filled in later by type checking.
  • Lowering. Name resolution gives each anonymous struct its own DefId, and AST lowering turns it into a real struct item. The struct shares its function’s generics, also when it’s nested in another one’s field, which is how its fields can use the function’s generic parameters, impl Trait, Self, and lifetimes without declaring any of them. Lifetimes elided in fields become early-bound parameters of the function, so the struct can use them too.
  • Types. After that a record is an ordinary ADT, its struct applied to the function’s own generic arguments. tcx.is_record tells it apart in the few places that care, like printing it the way closures are printed, {record@src/main.rs:6:9: 6:15}, and skipping it in item lints and dead code checks, since it’s documented and used through its function.
  • Type checking. The <_>::_ pattern takes its struct from the type it matches, and an inferred literal takes its struct from the expected type, which is also how _ { .. } builds and matches named structs.
  • Traits. In a trait impl, the parameter’s type isn’t the impl’s own anonymous struct. It’s the trait method’s struct, with the impl’s generic arguments filled in, and the fields the impl writes out are just checked against the trait’s by name and type, nested ones included. A method stays dyn compatible unless one of its fields mentions Self.

Rustdoc, Clippy, and rustfmt only needed small changes to match (Tooling).

The sugar

#![feature(struct_args, named_arguments, default_field_values)]

fn f(a: i32; x: i32, y: i32 = 0) {}
f(0, x: 1);

The sugar is smaller still, and almost all of it is in the parser.

  • Named arguments. Named arguments at the end of a call are parsed into one inferred struct literal, flagged so the pretty printer and rustfmt can print them back the way they were written. AST lowering adds the implied .. and tags the literal’s span (its location in the source) as coming from the named argument desugaring, the same way the code for for loops, ?, and a..b gets tagged. Type checking uses the tag to skip the default_field_values feature gate for the implied .., and error messages use it so a missing field is reported as “missing named argument width” instead of pointing at a .. nobody wrote.
  • ; parameters. These are handled entirely by the parser, which turns everything after the ; into the fields of a last TyKind::Record parameter, the same as writing struct { .. }.
  • Left-out structs. This is the only part that reaches type checking. When a call has one argument fewer than the function takes, and the last parameter is an anonymous struct whose fields all have defaults, the argument check skips that parameter and makes a note of the call. When building THIR, each of those calls gets a _ { .. } argument added, so MIR building and borrow checking see the call as if it had been written out.

2. Limitations and Open Questions

Nested anonymous structs

A field could also be an anonymous struct itself. Nesting isn’t new, with named structs it’s already valid Rust today:

struct Marker { at: Point }

fn i(Marker { at: Point { x, y } }: Marker) {}
i(Marker { at: Point { x: 1, y: 2 } });

This only binds x and y, the at field is taken apart but never bound.

Without elided patterns, an anonymous field is just another type, so it’s built and taken apart the same way:

fn j(_ { at: _ { x, y } }: struct { at: struct { x: i32, y: i32 } }) {}
j(_ { at: _ { x: 1, y: 2 } });

To keep at as well as its fields, bind it with an @. Since x and y are Copy, at and its fields can each have their own copy:

fn k(Marker { at: at @ Point { x, y } }: Marker) {}

The anonymous version is the same pattern with _ in place of the names:

fn l(_ { at: at @ _ { x, y } }: struct { at: struct { x: i32, y: i32 } }) {}

With fields that aren’t Copy, like a String, at and its fields can’t both own the same values, so the best you can do is borrow both:

struct Label { name: String }
struct Tagged { at: Label }

fn m(Tagged { at: ref at @ Label { ref name } }: Tagged) {}

And again anonymously:

fn n(_ { at: ref at @ _ { ref name } }: struct { at: struct { name: String } }) {}

Once the pattern is elided though, it’s not exactly clear how binding should work:

fn j(struct { at: struct { x: i32, y: i32 } }) {}

Elided fields can already take binding modes like ref, so the inner fields could too. Borrowing everything gives you at and its fields at once, just like ref at @ _ { ref x, ref y } did:

fn j(struct { ref at: struct { ref x: i32, ref y: i32 } }) {}

The biggest issue is name collisions. Binding fields at every level puts them all in the same scope, so two inner structs with the same field name clash:

fn o(struct { from: struct { x: i32 }, to: struct { x: i32 } }) {}

Binding only the outer fields never has this problem, since a struct’s field names are already unique. But I don’t think that’s the right call, it’s just the easy one. A collision like this could be an error, fixed by writing the pattern out and renaming them, like _ { from: _ { x: from_x }, to: _ { x: to_x } }.

Macros

Procedural macros get the tokens as written, and most of them parse those tokens with syn, which expects every parameter to be pat: ty, separated by commas. So syn rejects anonymous struct parameters, elided parameter types, and ; parameter lists, which means #[tokio::main] or #[tracing::instrument] can’t be used on functions that have them. Macros that parse the whole function body also fail on named arguments, since f(x: 1) isn’t an expression syn knows about. This isn’t unique to anonymous structs though. syn only started parsing RFC 3681’s = default fields in 3.0, so derives still built on syn 2 fail on structs that use them. syn 3.0 also anticipates several in-flight RFCs, so new syntax doesn’t have to wait until it’s close to stable to show up.

Every new form has a pat: ty spelling that fits what syn already has. p: struct { x: i32 } is already pat: ty, with struct { .. } as an opaque type. A bare struct { x: i32 } is _ { x }: struct { x: i32 }, using the inferred struct pattern. An elided parameter type can be read as what it stands for, Point { x, y }: Point, and a ; parameter list as a last struct { .. } parameter. They’re all just sugar, so a macro that prints the expanded form back out doesn’t change what the function means. That was a goal of the design, every parameter form should have a pat: ty version someone could write by hand.

Even once syn can parse these, some macros will need updating. A macro that just passes the signature through, as #[tokio::main] mostly does, would work right away. But #[tracing::instrument] records each parameter by its binding name, so it would need to know that an anonymous struct’s fields are its bindings.

macro_rules! has a subtler problem. Today a $p:pat, $e:expr (2024) or $s:stmt fragment at the end of a macro arm, given _ { x }, parses just the _ and leaves { x } behind, so the arm fails and a later arm, like (_ { $($t:tt)* }), can match. With _ { .. } patterns and literals the fragment takes the whole thing, so the earlier arm matches instead, which breaks existing macros even in crates that don’t use the feature. The fix is to keep the old behavior in those fragments: _ followed by { at the fragment’s outer level stays a lone _, which matches exactly what they did before. Nested inside brackets it was always an error, so it’s fine to allow there. Rust has changed what a fragment matches before, with pat_param in 2021 and expr_2021 in 2024, so a later edition could let them match _ { .. } too.

Prototype gaps

These are gaps in the prototype, or places where it had to pick something the design hasn’t decided yet:

  • Named arguments imply .. for every struct, named or anonymous, because the prototype adds the .. during AST lowering, before it knows which struct the call is for. Whether named structs should get it is undecided. If they do, a library adding a default to a field of a public struct changes which calls compile, so it depends on how #[non_exhaustive] ends up working with RFC 3681 defaults and with anonymous structs (API evolution and SemVer).
  • A function whose last anonymous struct can be left out still can’t be used as a value without it. For fn f(struct { a: i32 = 0 }), opt.unwrap_or_else(f) is an error. Making it work would mean f implementing FnOnce() as well as FnOnce(_) (Function types).
  • The macro_rules! fragments above still take _ { .. }, which needs the fix described in Macros before the prototype is compatible.
  • An elided parameter type is purely syntactic. A variant pattern like E::V(x) can’t elide its type even when E has a single variant and the pattern is irrefutable.
  • Rustdoc shows an anonymous struct parameter as _, without its fields.
  • Some error messages could be better, especially for mistakes in named arguments.
